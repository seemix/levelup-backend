# Чекліст запуску CRM

Порядок: бекенд (`levelup`) розгортається першим і сумісний зі старим фронтом (публічне API лендингу не змінилося), далі налаштування даних і smoke-тест, потім перемикання фронту (`levelup-front`) на власний онлайн-запис. Деталі середовища — [deployment.md](deployment.md).

Позначайте пункти `[x]` під час запуску. Відповідальний і дата: ______________________

## 0. Передумови
- [ ] Гілки `crm` обох репозиторіїв зелені: `pnpm typecheck && pnpm lint && pnpm test:int && pnpm test:e2e` (backend), `npm run lint && npx tsc --noEmit` (front).
- [ ] Обрано час запуску з мінімумом записів (ранок, до відкриття). Персонал попереджений.
- [ ] Майбутні записи EasyWeek вивантажені (список: дата, час, барбер, клієнт, телефон) — імпорту в v1 немає, їх доведеться внести вручну (п. 6) або обслужити в EasyWeek до кінця.

## 1. Бекап (обов'язково перед будь-якою зміною)
- [ ] `DATABASE_URL=... ./scripts/backup.sh /srv/backups 30` — дамп MongoDB і архів `media`.
- [ ] Бекап скопійовано на іншу машину/диск.
- [ ] Відновлення перевірено на тестовій базі: `mongorestore --gzip --archive=db-<stamp>.gz --nsFrom='levelup.*' --nsTo='levelup_restore.*'` — колекції й кількість документів збігаються.
- [ ] Записано поточний commit/тег, що працює в production (для відкату): `git rev-parse HEAD` → ______________

## 2. Сервер і змінні оточення
- [ ] MongoDB — replica set: `mongosh "$DATABASE_URL" --eval 'rs.status().ok'` → `1`; `DATABASE_URL` містить `replicaSet=…`.
- [ ] `.env` сервера: `PAYLOAD_SECRET` (не змінювати наявний — інакше всіх розлогінить), `FRONTEND_URL=https://levelupbalti.com`, `BACKEND_URL=https://admin.levelupbalti.com`, `COOKIE_DOMAIN`, `TRUSTED_PROXY_HOPS` (кількість проксі перед застосунком), `JOBS_AUTORUN=true`.
- [ ] Resend: домен у статусі **Verified** (SPF, DKIM, бажано DMARC), `RESEND_API_KEY` лише в `.env` сервера, `EMAIL_FROM_ADDRESS` на верифікованому домені, `EMAIL_FROM_NAME`.
- [ ] `NODE_ENV=production` (Dockerfile уже ставить) — тоді `pnpm seed` відмовить, а міграції застосуються на старті.

## 3. Розгортання бекенду
- [ ] Merge бекенду (див. п. 10, крок «backend») і збірка: `docker compose up -d --build` (або `pnpm build && pnpm start`).
- [ ] Міграції: `pnpm migrate` (або автоматично на старті). У лозі — `Migrated:` для кожної нової міграції без помилок; перевірка: `mongosh "$DATABASE_URL" --eval 'db["payload-migrations"].find({}, {name:1}).toArray()'` містить усі імена з `src/migrations/index.ts`.
- [ ] `GET https://admin.levelupbalti.com/api/health` → `{"status":"ok"}`.
- [ ] Лендинг на старому фронті працює як раніше (барбери, слайди, «Про нас», медіа), editor редагує контент.
- [ ] Існує локація за замовчуванням «Bălți, Decebal 142» (ru/ro/en) — перевірити адресу, телефон, `mapUrl`.

## 4. Користувачі й ролі (admin)
- [ ] Наявні користувачі зберегли ролі; додано ролі: власник — `admin`; адміністратор салону — `manager` з `locations`; кожен барбер — `barber`.
- [ ] Кожен барбер-користувач прив'язаний у картці барбера (`barbers.user`, рівно один барбер на користувача).
- [ ] Паролі видано особисто; кожен увійшов і обрав мову адмінки.

## 5. Каталог, барбери, налаштування
- [ ] Категорії, послуги, додаткові послуги — назви й описи ru/ro/en, ціни, тривалість, `active`, `onlineBooking`, `appliesTo` додаткових послуг.
- [ ] Барбери: `active`, `onlineBooking`, колір, локації, список послуг, тижневий графік, винятки (відпустки), `%` послуг і `%` додаткових (рішення 10), перевизначення цін (`barber-prices`).
- [ ] `booking-settings`: крок 15 хв, мінімум 2 год, горизонт 30 днів, скасування ≥ 3 год, нагадування 24 год, `onlineBookingEnabled`, відправник/`replyTo`.
- [ ] Промокоди (якщо є).

## 6. Каси й початкові залишки (admin)
- [ ] Каси для кожної локації (наприклад «Наличные», «Терминал (карта)») і категорії витрат.
- [ ] Перерахувати готівку фізично. Для кожної каси — операція `adjustment` (admin, тип «Коригування»): сума = фактичний залишок, коментар «Початковий залишок <дата>», `occurredAt` — момент запуску.
- [ ] Наявні проданi паперові сертифікати (якщо вносяться): «Продаж сертифіката» на залишок + `adjustment` з мінусом на ту саму суму й коментарем «перенесення сертифіката <код>» — гроші вже були отримані раніше, баланс каси не змінюється.
- [ ] `RECALC_DRY_RUN=true pnpm crm:recalc-balances` — розбіжностей немає; баланси на сторінці «Каси» = фактичні.
- [ ] Майбутні записи з EasyWeek внесено в календар (персонал, «Новий запис») — або вирішено обслужити їх в EasyWeek.

## 7. Smoke-тест на production (до перемикання фронту)
Використовувати тестовий телефон і свій e-mail; після тесту — скасувати.
- [ ] Онлайн-запис через API: пройти `docs/api-booking.http` проти production (config → days → slots → quote → create). Браузерний preview фронту з іншого домену CORS не пропустить (дозволено лише `FRONTEND_URL`), тому запис через сам лендинг перевіряється в п. 8.
- [ ] Лист-підтвердження прийшов (мова — мова форми), у Resend → Emails статус `delivered`, в історії запису є `email`.
- [ ] Посилання скасування з листа відкриває сторінку й скасовує запис; прийшов лист «скасовано».
- [ ] Під admin / manager / barber: календар (день і тиждень), створення й перенесення запису, оплата 2 касами + чайові на тестовому записі, refund (admin) — баланси кас повернулися; звіти клієнтів/фінансів/зарплати відкриваються, CSV завантажується.
- [ ] Barber не бачить чужих оплат, кас із балансами, звітів, крім своєї зарплати; manager — лише свої локації.
- [ ] Нагадування: запис на «завтра в цей час + 5 хв» отримав лист-нагадування (або перевірити `reminderSentAt` наступного дня).
- [ ] `RECALC_DRY_RUN=true pnpm crm:recalc-balances` після тестових оплат — без розбіжностей.

## 8. Перемикання фронту на власний онлайн-запис
- [ ] У production-середовищі фронту: `NEXT_PUBLIC_BOOKING_PROVIDER=native` (змінна build-time — потрібен **новий деплой**), `NEXT_PUBLIC_API_URL`/`NEXT_PUBLIC_BACKEND_URL` — production (або не задані).
- [ ] Merge фронту (п. 10, крок «frontend») і деплой.
- [ ] На `levelupbalti.com` у трьох мовах: кнопка «Записатися» відкриває секцію запису, віджет EasyWeek не завантажується, секція «Послуги» бере дані з CRM.
- [ ] Тестовий онлайн-запис із телефону (мобільна верстка) → видно в календарі → скасувати.
- [ ] EasyWeek лишається паралельно для вже наявних записів (A3); нові записи там вимкнути/приховати. Дата повного вимкнення EasyWeek: ________

## 9. Після запуску (перший тиждень)
- [ ] Uptime-монітор на `/api/health`, логи `docker compose logs -f payload` (помилки jobs, Resend).
- [ ] Щоденний бекап за cron (`scripts/backup.sh`), перевірено наявність файлів.
- [ ] Наприкінці першого дня: `RECALC_DRY_RUN=true pnpm crm:recalc-balances`, звірка кас із фактом, фінансовий звіт за день.
- [ ] Збір зауважень персоналу.

## 10. Merge гілок `crm` → `master` (в обох репозиторіях)
Виконувати в момент розгортання відповідної частини (бекенд — п. 3, фронт — п. 8).
```bash
# backend
cd levelup
git checkout master && git pull
git merge --no-ff crm -m "Merge crm: CRM launch"
pnpm install && pnpm typecheck && pnpm lint && pnpm test:int
git tag crm-launch-backend && git push origin master --tags

# frontend
cd ../levelup-front
git checkout master && git pull
git merge --no-ff crm -m "Merge crm: native online booking"
npm ci && npm run lint && npx tsc --noEmit
git tag crm-launch-front && git push origin master --tags
```
- [ ] Конфлікти відсутні або розв'язані без втрати змін `master`.
- [ ] Гілку `crm` не видаляти до кінця першого тижня (відкат/порівняння).

## 11. План відкату
Рішення про відкат — якщо онлайн-запис або календар не працюють і швидке виправлення неможливе.
1. **Фронт (найшвидше, хвилини):** повернути `NEXT_PUBLIC_BOOKING_PROVIDER=easyweek` і передеплоїти (або перевідкрити попередній деплой). Записи, створені в CRM до відкату, лишаються в базі — переглянути календар і перенести їх в EasyWeek / обдзвонити клієнтів.
2. **Бекенд:** розгорнути тег/commit із п. 1 (`git checkout <commit>` → збірка). Міграції CRM лише додають колекції, поля й індекси; старий код їх ігнорує, тому база сумісна (`down`-міграції навмисно нічого не видаляють).
3. **База (крайній випадок — пошкодження даних):** зупинити застосунок, `mongorestore --drop --gzip --archive=db-<stamp>.gz`. Усе, що створено після бекапу (записи, оплати), буде втрачено — перед цим вивантажити `appointments` і `transactions` (`mongoexport`) для ручного відновлення.
4. Після відкату — записати причину й час, вирішити дату повторного запуску.
